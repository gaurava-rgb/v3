## Assessment

No evidence of recent local code corruption: tracked working tree was clean, latest commit dates to August 14, and the sole pre-existing untracked file was sample.txt. The project has understandable separation between bot, database, routes, and rendering. However, real reliability, privacy, and authorization defects make the prior blanket statement that “the code is fine” too strong.

The conversation reports the bot disconnected September 28 and restarted October 6 at 6:04 PM CDT (UTC-5), plus two dashboard workers despite configuration specifying one. Neither is independently reverified here. Cloudflare/IPv6 was a disproved hypothesis in the conversation, not an established cause. Current browser navigation took approximately 1.8 seconds for rides and 2.6 seconds for housing; this small sample cannot resolve earlier 10–16 second delays.

## Priority findings

1. **High — disconnected bot can remain apparently healthy indefinitely.** `bot.js:417–419` sets isReady=false on disconnect; watchdog at `591–597` immediately skips disconnected states. Reconnect has no overall deadline, and unhandled rejections at `614` are only logged. A reconnect that rejects or hangs can leave the process running with no functioning WhatsApp connection. This is consistent with the supplied outage narrative, but logs are needed to prove its exact trigger. Add bounded reconnect attempts/deadlines and health based on connection/activity, not only PM2 status.

2. **High — housing contact gating leaks through original messages.** `lib/views.js:907–909,985` includes unredacted message_text for anonymous visitors as well as verified users. Original phone numbers, names, or contact instructions remain accessible despite the contact gate. Synthetic anonymous rendering reproduced a phone number in the output. Redact contact data or restrict the original message to authorized tiers.

3. **High — known fallback key permits forged phone sessions if secret is missing.** `middleware/auth.js:13,25–31,78–84` uses a public literal as the default signing secret and grants valid phone cookies T2 access. The local .env lacks WA_OTP_SECRET, verified without displaying secret values. VPS settings were not inspected, so production exploitability remains conditional. Fail startup or disable this session mechanism when a strong secret is absent; rotate the secret and invalidate prior sessions if the fallback has been used.

4. **High — submissions can impersonate another phone.** `routes/submit.js:26,56–57,82` stores the browser-supplied phone instead of the authenticated verified phone. The UI's readonly input is not server-side enforcement. A verified user can attribute a post to another number and then fail ownership checks for their own submission. Derive ownership from the authenticated identity.

5. **High — transient ingestion failures can permanently discard listings.** `bot.js:104` marks an ID processed before parsing/storage. It logs the parse result before saving the listing; `db.js:177–189` considers any message-log entry processed, including failures. History recovery skips those IDs. Track successful persistence separately and retain retryable failures.

6. **High — failure loading monitored groups opens ingestion to all joined groups.** `db.js:49–51` returns [] on query failure; `bot.js:59–63` clears the allowlist. Live/history filters at `187,504` only restrict ingestion when that set is nonempty. A DB failure or deliberate deactivation of every group can therefore monitor unintended groups. Retain the last valid allowlist and fail closed.

7. **Medium — edit/delete endpoints can report success when writes fail.** `db.js:592–665` ignores Supabase returned errors. Failed edit writes may be followed by match deletion, and routes can redirect as if successful. Check every mutation and make related operations transactional where possible. Edit rematching at `627–632` also bypasses scoring and quality calculation.

## Other functional findings

- **Backfilled relative dates use reconnect day:** `bot.js:116–118` calculates sentAt but omits the parser's third argument; `parser.js:196` defaults to now. “Tomorrow” in historical messages can become the wrong date.
- **Matches can be misleading:** actual matcher functions give an 08:00 College Station→Houston need and a 20:00 Austin→Houston offer score 0.8 and quality “strong” (`matcher.js:40,110–125`; threshold defaults to 0.5). Different origins and distant times should be evaluated as compatibility constraints.
- **Suggested matches consume availability:** `db.js:466–469` marks both requests matched, while candidates must be open (`410`). Further riders can lose a still-available offer without anyone confirming the match.
- **Multiple dates/return legs miss immediate matching:** saveRequest inserts several rows but returns one (`db.js:283–285,339–395`); the bot matches only that row (`bot.js:160`).
- **Same-day evening rides are blocked:** `routes/submit.js:49–50` uses UTC today. After 7 PM CDT / 6 PM CST, the current Central date appears past. The modal's minimum date uses UTC too.
- **Housing dates show one day early:** `lib/views.js:876–877,1368–1371` converts date-only values from UTC midnight to Chicago. Synthetic October 6 rendered October 5.
- **Housing filters override one another:** `lib/views.js:1230–1248,1264–1274` apply separate visibility rules. Actual generated JS reproduced a $1,000 listing becoming visible after a type change with a $600 price limit still selected.
- **Malformed phone cookie returns 500:** `middleware/auth.js:42` compares unequal-length buffers outside the try. Locally reproduced RangeError with `abc.x`; Express 5 should fail the request rather than crash the process.
- **Secondary linked phones fail ride ownership:** profile lists all linked numbers but `routes/rides.js:39` expects req.user.phones, which authentication never populates. Only one phone is selected for email sessions.
- **Logout deletes auth state automatically:** `bot.js:425–428` removes .v3_auth, contrary to the repository instruction to preserve it. Not established as the cause of this outage.

## Deployment checks still needed

- Confirm dashboard worker count and effective PM2 configuration; supplied chat reports two, ecosystem.config.js specifies one.
- Verify production signing secret. KAPSO_VERIFY_SECRET is set locally, but `routes/verify.js:63–70` skips webhook authentication entirely if absent in another environment.
- Confirm monitor port 3005 is private: monitor binds all interfaces without authentication and includes process logs/group-message snippets (`monitor.js:195–263,275,316`).
- Review proxy trust/rate limiting: dashboard has no trust proxy setting. Behind a conventional nginx proxy, limits may apply collectively to its IP instead of individual visitors.
- Add request/upstream timing before assigning website slowness to Cloudflare, Supabase, or origin networking. No causal conclusion is justified from this audit's limited timings.
- Check housing expiry automation: application queries active=true but no end-date expiry job was found; database automation could exist independently.

## Verification

All 51 existing parser/matcher tests passed using dependencies installed in /tmp and dummy local Supabase configuration, without production DB access. A plain test invocation initially failed because local dependencies were absent; after installing them, matcher import additionally required Supabase environment configuration. The suite contains no route/auth/rendering tests, so its green result does not cover the defects above.

Live embedded rides/housing scripts compiled successfully. The rides destination filter executed without error. Synthetic rendering and isolated VM checks reproduced privacy, date, filter, matcher, and malformed-cookie defects. No live submissions, login attempts, verification calls, or outbound messages were made.

Recommended order: close identity/privacy gaps; make bot reconnect and ingestion retry reliable; then correct matching/edit behavior and dates. Investigate website latency separately with production timing evidence.
